# PIT mutation testing: LLM-generated vs. developer-written tests

Replication package for the mutation-testing experiment: 18 open-source Java projects, four LLMs
(Claude, GPT, Gemini, DeepSeek) and the developer-written tests of each project, evaluated with
[PIT](https://pitest.org) 1.30.1.

> **Status:** `data/generated_tests/` (the 360 generated suites) is to be added by the authors.
> Everything else in this repository reproduces the reported mutation-testing results.

## Contents

```
data/
  pit_reports/<project>/mutations_{Claude,GPT,Gemini,DeepSeek,Human}.xml   90 raw PIT XML reports
  pit_reports_manifest.csv                                                  size and MD5 of every report
  generated_tests/                                                          generated test suites + selection.csv (see its README)
results/
  mutation_scores_90.csv    mutation score of every project x suite (90 rows)
  mutant_categories.csv     mutant categories per project + TOTAL row
  bootstrap_ci.csv          95% bootstrap confidence intervals
scripts/
  match_mutants.py          matches mutants across the five suites of one project and classifies them
  build_results.py          rebuilds mutation_scores_90.csv and mutant_categories.csv from the raw reports
  bootstrap_ci.py           bootstrap CIs over the 18 projects
```

## Reproduce the results

Requires Python 3.9+ with `pandas` and `numpy` (`pip install -r requirements.txt`).

```bash
cd results
python ../scripts/build_results.py ../data/pit_reports     # scores + mutant categories from the raw XML
python ../scripts/bootstrap_ci.py                          # confidence intervals
```

On Windows use backslashes (`..\scripts\build_results.py ..\data\pit_reports`). The three CSV files are
regenerated byte-for-byte.

## Method

**Test-suite selection.** For each project-LLM pair five suites were generated for the consistency
analysis (18 x 4 x 5 = 360). The 72 suites evaluated with PIT are Run 1 of each pair. No filtering on
coverage or mutation results was applied. Scores therefore come from a single run per pair.

**PIT configuration.** PIT Maven plugin 1.30.1, one run per suite, for example:

```
mvn org.pitest:pitest-maven:mutationCoverage -DtargetClasses=jenkins.plugins.publish_over_ftp.*,jenkins.plugins.publish_over_ftp.descriptor.*,jenkins.plugins.publish_over_ftp.options.* -DtargetTests=jenkins.plugins.publish_over_ftp.jenkins.IntegrationTest_gemini -DoutputFormats=XML,HTML -DtimestampedReports=false
```

No mutators, timeout or thread options were passed, so PIT's defaults apply (default mutator group).
The JUnit 5 plugin for PIT (`pitest-junit5-plugin`, versions 1.1.2-1.2.3 depending on the project) only
lets PIT run JUnit 5 tests and does not change which mutants are generated.

**Mutation score** = killed / total mutants, where *killed* means PIT status `KILLED` or `TIMED_OUT`.
`SURVIVED` and `NO_COVERAGE` mutants count as not killed (no-coverage mutants stay in the denominator).

**Mutant identity.** The five reports of a project list the same mutants. A mutant is identified by
mutated class + method + method descriptor + line number + mutator + instruction index + block. The scripts
stop with an error if the mutant sets of the five suites differ (no mutant is dropped silently); this never
happened in the 18 projects.

**Mutant categories** (LLMs = Claude, GPT, Gemini, DeepSeek):

| Category | Definition |
|---|---|
| all killed | developer tests and all four LLM suites detect the mutant |
| LLM-only | developer tests miss it, all four LLM suites detect it |
| developer-only | developer tests detect it, no LLM suite does |
| neither | no suite detects it |
| mixed | every other combination |

`llm_only_any` in `mutant_categories.csv` is the looser variant (developer tests miss it, at least one LLM detects it).

**Confidence intervals.** Percentile bootstrap over the 18 projects (whole projects resampled, 10,000
resamples, seed 42) of the mean project-level score and of the mean paired difference (LLM - developer
tests). `bootstrap_ci.csv` also contains a sensitivity analysis without the three projects in which the
developer suite scored 0.

## Main results

| Suite | Mean score | 95% CI |
|---|---|---|
| Claude | 0.528 | [0.368, 0.683] |
| GPT | 0.476 | [0.320, 0.630] |
| Gemini | 0.430 | [0.288, 0.574] |
| DeepSeek | 0.482 | [0.334, 0.624] |
| Developer tests | 0.378 | [0.229, 0.528] |

Over the 18 projects (3,216 mutants): 560 mutants killed by all suites, 56 LLM-only, 27 developer-only,
2,162 killed by none, 411 mixed.

## Notes and known issues

* **vaulttec-sonar-auth-oidc** was run with mutators outside PIT's default group (`RemoveConditional*`, `Switch`)
  that no other project has. They account for 73 of its 164 mutants and are ignored by the scripts (91 mutants
  remain) so that all 18 projects use the same mutator set. Use `--all-mutators` with `match_mutants.py` to keep them.
* **Three projects have a developer-suite score of 0** (Trendyol-redis-slack-bot, arteam-dropwizard-http2-client,
  eclipse-tractusx-managed-service-orchestrator). In arteam the developer tests cover none of the 97 mutants.
  The cause was not investigated. The sensitivity analysis in `bootstrap_ci.csv` shows how the comparison changes
  without them.
* **jenkinsci-publish-over-ftp-plugin:** the original Claude XML report had stray text after the closing
  `</mutations>` tag; the copy stored here is the well-formed report. The Gemini report is a re-run.
* PIT marks timed-out mutants as detected, and timeouts are not fully deterministic: re-running a suite can
  change a few mutants. The reports in this repository are the ones the results were computed from.
